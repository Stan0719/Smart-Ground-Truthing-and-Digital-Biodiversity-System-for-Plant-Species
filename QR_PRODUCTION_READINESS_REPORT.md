# QR Production Readiness Report

## Decision: NOT READY

Migration 015 passed local Docker verification, but the supplied production
facts show unresolved application-data and security questions. No production
connection or database operation was performed for this report. The live
facts below are from the project team’s prior read-only inspection and have
not been independently verified.

## Supplied production state

- `public.qr_code` exists with 18 rows: 16 assigned and 2 unassigned.
- `plant_app.qr_code` is absent.
- Both `plant_app.plant_record` and `public.plant_record` exist, with 18
  plant records.
- The QR table has the reviewed eight-column shape, `qr_id` is a bigint
  `GENERATED ALWAYS` identity, `plant_id` is nullable bigint, and the expected
  primary/unique constraints are present.
- The QR-to-plant FK points to `plant_app.plant_record(plant_id)` with
  `ON DELETE SET NULL`.
- `plant_app.visitor_scan_history.qr_id` references `public.qr_code` with
  `ON DELETE SET NULL`; that table has 18 rows.
- `public.qr_scan_history.qr_id` references `public.qr_code` with
  `ON DELETE CASCADE`; it currently has zero rows.
- Four visitor scan rows refer to QR IDs 4, 5, 13, and 15; supplied inspection
  says those relationships match.
- Two plant rows, IDs 1 and 4, have QR tokens without inventory rows. Their
  tokens differ from the two unassigned inventory tokens. No reassignment or
  token repair is authorized by these facts.
- No `plant_app.schema_migration_history` table was found, and the Supabase
  migration listing returned no entries. Neither fact proves that a migration
  was never manually applied.
- Supplied privilege checks say `postgres` has full table rights and the
  backend’s configured URL username is the project-scoped pooler form for that
  role. Browser API roles lacked CRUD on the inspected QR/plant objects but
  had some unusual `TRUNCATE`, `TRIGGER`, and `REFERENCES` privileges on public
  tables.

## Migration and dependency findings

### Migration 015

The migration moves the table using `ALTER TABLE ... SET SCHEMA` within an
explicit transaction. It preflights the source and destination locations,
column/index/constraint shape, outgoing and incoming foreign keys, sequence
ownership/location, and unexpected catalog dependencies. Its reviewed source
shape is compatible with the supplied production table. It does not reconcile
plant records, assign QR codes, change grants, or configure Supabase Data API
exposure/RLS.

The move should preserve rows, constraints, indexes, owner and table ACL. The
destination schema’s `USAGE` privilege and the moved identity sequence’s ACL
remain separate checks. The public scan-history FK should continue to point to
the same table object after its schema move. The 18 visitor scans and four
referenced QR IDs make post-move FK and history verification mandatory.

### Migration 003 and data integrity

The current repository copy of migration 003 uses a consistent `p` alias; the
reported `ASp`/`p` alias defect is not present in the inspected working copy.
Its SQL was exercised against a disposable PGlite fixture. When the fixture
contains 16 matching rows, two plants with missing QR inventory rows, and two
unassigned inventory tokens, 003 inserts two rows using the plants’ existing
`qr_token` values and leaves the two spare unassigned tokens unchanged.

That fixture demonstrates behavior; it is not approval to perform that data
change in production. On the supplied production state, 003 would add inventory
rows for plant IDs 1 and 4 using their existing plant tokens. The current
runner’s stricter adoption check classifies the supplied partial state as
ambiguous and stops. A project owner must decide whether those two inventory
rows should be added through a reviewed remediation plan. Do not use the two
spare tokens to “repair” those plants, and do not mark 003 complete based only
on 16 of 18 mappings.

### Migration 014 and history

Migration 014’s expectations do not match the supplied source table: it expects
`GENERATED BY DEFAULT`, an integer `plant_id`, and text `status`; production has
`GENERATED ALWAYS`, bigint `plant_id`, and `varchar(30)` status. It is not safe
to replay. In its transaction, it may move the table before discovering the
incompatibility, but an exception should roll the transaction back; that is
not a reason to try it.

The repository’s general runner recognizes complete 015 structure and records
014 as superseded, but it has a loopback-only target guard. The dedicated
QR-only runner also restricts itself to a fixed local database. Neither is a
production command. Legacy ledger rows without checksums intentionally block
the general runner for operator review. Production ledger history is currently
reported absent, but a future production history record must distinguish
`executed`, `recognized`, and `superseded`; a recognition timestamp must not be
described as the migration execution time.

The supplied Supabase migration list is empty, but manual SQL execution is not
captured by that listing. Production SQL/catalog state remains authoritative.

## Security and application compatibility blockers

1. The application uses the elevated `postgres` PostgreSQL role according to
   supplied inspection. This role has full privileges and bypasses RLS. The
   runtime connection is not least privilege.
2. `plant_app.visitor_scan_history` has RLS enabled and no policies are created
   by migration 010. Its current `postgres` runtime can bypass RLS. A custom
   runtime login cannot be assumed to work until its policy/ownership model is
   designed and tested.
3. The project team has not supplied the exact production Data API exposed
   schema list. Keep `plant_app` unexposed unless direct API access is
   intentionally designed. Current repository QR calls are backend PostgreSQL
   queries, not mobile direct PostgREST queries.
4. The production schema-level `USAGE`, moved table ACL, and QR identity
   sequence ACL for a future least-privilege runtime role have not been
   verified.
5. `anon`, `authenticated`, and `service_role` had unusual elevated
   `TRUNCATE`, `TRIGGER`, or `REFERENCES` rights on some public tables. The
   exact affected relation/grant source must be established before any revoke.
6. Two plant tokens lack inventory rows. This could cause QR lookup/listing and
   assignment workflows to disagree with `plant_record` even after table
   movement. Migration 015 preserves that state; it does not resolve it.
7. No production-safe migration runner/history registration process is
   provided in the repository. The local runners and general `npm run migrate`
   are not suitable substitutes.

## Rollback and recovery

Migration 015 is transactional, so any failure before its internal `COMMIT`
should leave the source table in `public`. Confirm rollback and stop on any
preflight failure.

After commit, a schema-only reverse move may be possible if no conflicting
`public.qr_code` exists and the old application version is restored. This must
be rehearsed on a restored disposable copy. Pause QR writes/scans during the
rollback decision. A schema move back retains post-migration table data, but
application writes and changed permissions/RLS behavior still require review.
Do not overwrite production from a backup as an automatic rollback: restore to
a separate recovery target first, compare post-backup writes, then use the
approved recovery procedure.

## Readiness gates

Do not approve production execution until:

- A complete production backup is restored and verified in an isolated target.
- Read-only production inspection confirms migration preconditions and the
  exact dependencies/owner/ACL/RLS state.
- The project owner resolves plant IDs 1 and 4 without reassigning spare QR
  tokens by assumption.
- Runtime and migration roles are separated or the elevated-role exception is
  formally accepted with compensating controls.
- Supabase Data API exposure, grants, and RLS policies are reviewed.
- A production-only execution and post-run history-registration process is
  written, reviewed, and authorized. Do not run the local/general repository
  runners against production.
- The team approves a tested rollback/recovery plan and operational window.

Until all gates pass, the migration remains **NOT READY FOR PRODUCTION**.
