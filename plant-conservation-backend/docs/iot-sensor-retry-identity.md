A device row lock serializes per-device identity checks. Exact key/payload replay returns recorded:false; changed payload409. Existing pre-cutover raw receipt keys still work. New readings never create sensor_reading rows. Captured timestamp ordering/dedup remains unchanged. Distinct key-only readings at the same clock count separately. A new receipt and accepted checkpoint/aggregate/threshold-alert effects commit atomically; failure rolls everything back and leaves memory unchanged. Durable checkpoint is read under lock, including across workers/restarts.

Checkpoint cadence intentionally changes: every accepted reading persists its bounded per-device accumulator, instead of leaving accepted counts only in memory for60seconds. This is needed so a durable dedup receipt cannot outlive its count. Completed10-minute aggregates and active checkpoints remain the report source; no duplicate raw writes. This adds a checkpoint upsert and (for keyed inputs) one compact receipt insert per reading. No automatic retention/pruning is implemented: deleting identity metadata would weaken replay protection. Storage growth/write throughput require measured deployment planning; no load result is claimed.

Before033, key-only accepted submissions left no reconstructable durable key history. This migration cannot recover those prior identities. Capture-only stale ordering follows the existing contract; no claim of globally reconstructing old capture payloads is made. Inputs without a key have no durable key identity.
